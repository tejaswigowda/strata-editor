Make a Pythagorean-theorem short

A two-minute proof that 3² + 4² = 5², with subtitles. It starts with fifty tiles, one triangle and three labels; then the camera makes quarter turns to show two more triples, 5-12-13 and 8-15-17, and a last one to an end card. It is built entirely by hand, no AI, with the JS Shell and the Universal Timeline. Open the editor, open the Shell tab, and paste each block in order — or open the finished scene, pyth.json (step 13).

Why the Shell, not clicking. Every edit below is a real, undoable, git-diffable command (editor.execute(...) under the hood) — the Shell is just the fastest way to author them. You can always inspect or hand-tweak the result afterward in the Outliner/Object panel; nothing here is a special "script mode."
One paste, one scope. The Shell does not keep variables between pastes, so every block below is self-contained: it defines what it uses, and anything a later block needs is found again by name or class ($S('#three'), $S('.cube')). Start from an empty scene.

1 Build the three squares out of tiles

The proof needs the squares to come apart and go back together, so each one is made of unit tiles instead of one big box. A tile is a 1×1×1 cube, so it reads as a solid block from any side when it tumbles later. Tiles sit in a row or a column group, and the group sits in a square group: #3x3-square › #3col1 › cube_3.1.1. That nesting is what lets the timeline say "the first column of the 3×3" later.

// A square of side n is n lines (rows or columns) of n tiles. Each tile is a
// 1 x 1 x 1 cube; each line is its own group so the timeline can address it.
function makeSquare(n, name, color, kind, place) {
  const square = new Group();
  square.name = name;
  for (let k = 1; k <= n; k++) {
    const line = new Group();
    line.name = `${n}${kind}${k}`;
    for (let m = 1; m <= n; m++) {
      const tile = new Mesh(
        new BoxGeometry(1, 1, 1),
        new MeshStandardMaterial({ color, roughness: 0.6, metalness: 0.2 })
      );
      tile.name = `cube_${n}.${k}.${m}`;
      tile.position.set(...place(k, m), 0);
      tile.castShadow = tile.receiveShadow = true;
      tile.userData.hasEdgeOutline = true; // black border, drawn by the viewport
      line.add(tile);
    }
    square.add(line);
  }
  editor.execute(new AddObjectCommand(editor, square));
  return square;
}

// 3x3 on the vertical leg: columns, column 1 touches the triangle.
makeSquare(3, '3x3-square', 0xff6b6b, 'col', (k, m) => [1 - k, 3 - m]);
// 4x4 under the horizontal leg: rows, row 1 touches the triangle.
makeSquare(4, '4x4-square', 0x4ecdc4, 'row', (k, m) => [m, -k]);
// 5x5 on the hypotenuse: built upright, then turned onto the slope.
const big = makeSquare(5, '5x5-square', 0x333300, 'row', (k, m) => [m - 0.5, 5.5 - k]);
big.position.set(4.5, -0.5, 0);
big.rotation.z = Math.atan2(4, 3);   // 53.13 degrees, the angle of the 3-4-5 triangle

Give everything an addressable class — squares, lines and tiles — so selectors like #3x3-square #3col1 .cube and .cube work. Class names are stored lowercase, so use lowercase everywhere:

$S('#3x3-square, #4x4-square, #5x5-square').addClass('square');
$S('#3x3-square > *').addClass('col');
$S('#4x4-square > *, #5x5-square > *').addClass('row');
$S('#3x3-square > * > *, #4x4-square > * > *, #5x5-square > * > *').addClass('cube');
$S('.cube').nodes.filter(n => n.name.startsWith('cube_')).length   // 50 tiles: 9 + 16 + 25
Selectors reach down. A class on a node also matches everything inside it, and each tile's black border is a child of the tile, so $S('.cube').nodes.length says 100, not 50: the 50 tiles and their 50 borders. That is harmless — the borders follow their tiles through every fade and flight, and moveToEach pairs borders with borders in the same order — but it is why the check above filters by name.
Why the 5×5 is built upright and then turned. Its tiles end up lying on the hypotenuse, so the whole group is rotated by the triangle's angle. Because the rotation lives on the group, every tile inherits it — and when the other 25 tiles later fly onto these cells, they turn to match. You never type a rotation for an individual tile.

3 Three text labels

Text isn't scriptable from the Shell directly (font loading needs the UI's loader) — use the Text stencil three times, then rename each one. This is the one click-driven step before the camera.

4 Background and a glow for the text

makeTexture is a Shell helper — hand it a function that paints a 2D canvas, and it returns a ready-to-use texture. The default environment lights the scene from the background, so ask for it to be rebuilt once the background changes, otherwise the tiles keep the old, brighter lighting. Text lit only by scene lights goes faint on a dark ground, so give the labels some light of their own:

scene.background = makeTexture((ctx, size) => {
  const g = ctx.createLinearGradient(0, 0, 0, size);
  g.addColorStop(0, '#1b2340');
  g.addColorStop(0.55, '#141a2e');
  g.addColorStop(1, '#0a0d18');
  ctx.fillStyle = g;
  ctx.fillRect(0, 0, size, size);
}, 512);
setEnvironment('Default');   // rebuild the image-based lighting from the new background

// text lit only by scene lights goes faint on a dark ground: give it a glow of its own
$S('.label').nodes.forEach(o => {
  o.material.emissive = new Color(0xffffff);
  o.material.emissiveIntensity = 0.7;
  o.material.needsUpdate = true;
});

// white text over a bright tile needs an edge: a black drop shadow, offset down and to the right
$S('.label').nodes.forEach(o => { o.userData.textShadow = true; });

The shadow is a black copy of the label that the editor draws behind it and keeps in step with it: it follows every change(), every fade and every move, so it needs no keyframes of its own. It is not saved in the scene; only the textShadow flag is. Give userData.textShadow an object, such as { size: 0.1 }, for a longer shadow. Cues on the video use the same idea: the subtitles have a black outline and shadow too.

Keep the text out of the subtitle band. Subtitles are drawn over the bottom sixth of the frame, and a two-line cue is taller than a one-line one. Anything the film writes in the world has to stay above that band, or a caption and a cue sit on top of each other and neither can be read. That is why the 4 label sits beside the 4×4 rather than under it, why the sum row is at y = −3.1 (low enough that b has room above the theorem, high enough to clear the cues), and why the two extra triples, with their captions, are raised 2.2 units in step 9. Check any placement by scrubbing to a time when a two-line cue is on screen.

5 The camera and the end card

The film is shot by a camera that lives in the scene, so it can be animated and chosen as a render shot. It looks straight down −Z at the middle of the figure. The rest of the film is the camera turning on the spot, a quarter turn at a time: left to a second triple, round to a third, and finally to the end card, which sits 15 units off to the camera's right.

const cam = new THREE.PerspectiveCamera(50, 16 / 9, 0.1, 2000);
cam.name = 'PerspectiveCamera';
cam.position.set(3, 0.68, 20);              // dead-centre on the figure, looking down -Z
editor.execute(new AddObjectCommand(editor, cam));

Open Stencils → Mesh → Call card and click it. It inserts an addressable plane that embeds the current /about/callcard live and fits it to the viewport camera. Move it off to the camera's right instead, make it landscape, and hide it until the reveal:

const card = $S('#callcard').nodes[0];
card.userData.width = 3.2;                  // landscape: the stencil's portrait 1.8 x 3.2 swapped
card.userData.height = 1.8;
card.geometry = new PlaneGeometry(3.2, 1.8);
$S('#callcard').moveTo(18, 0.68, 20).scaleTo(8);   // 15 units to the camera's right, 8x bigger
card.rotation.set(0, -Math.PI / 2, 0);             // front face toward the camera's start position
card.material.opacity = 0;
Three details in that block. scaleTo sets an absolute scale; scale would multiply the size the stencil already gave it. A mesh's front is its local +Z, so turning the card a quarter turn about Y (−90°) points that front back at the camera's start position; if you get it backwards the card shows mirrored (it is double-sided, so it never disappears). And the card is hidden by being fully transparent, not by visible = false, because the reveal only animates opacity. The viewport may show the card stretched until it is re-baked: the Render tab does that, and so does reopening the saved scene.

Why a sliver first. The 3 and the 4 are lengths before they are areas. The first column is squashed to 0.2 of a tile wide and moved 0.4 along so it hugs the leg like a ruler (positionX: 0.4, scaleX: 0.2); at 14 s it relaxes to positionX: 0, scaleX: 1 and the other two columns fade in beside it. 7 The proof: 9 tiles and 16 tiles onto 25 cells

The 5×5 is only a landing pad. Make it invisible from the first frame, then send every tile of the other two squares onto one of its cells. moveToEach pairs sources to targets by order: the sources are listed 3×3 first, so the nine red tiles take the first nine cells (row 1 and the first four of row 2) and the sixteen teal tiles take the rest.

// the 5x5 is only a landing pad: start it transparent so it is never seen, not even at 0 s
$S('#5x5-square .cube').nodes.forEach(t => { t.material.transparent = true; t.material.opacity = 0; });
$S('#5x5-square, #5x5-square *, #5x5-square .cube').at(0).fadeOut(1);

// the proof: 9 tiles + 16 tiles tumble onto the 25 pad cells, 3 seconds, in selector-list order
$S('#3x3-square .cube, #4x4-square .cube').at(40).moveToEach('#5x5-square .cube', 3000, {
  spin: [1, 1, 0], arc: 3, stagger: 0.4, easing: 'ease-in-out'
});
Why 3 seconds, and why a pad. Twenty-five tiles at once blur under about a second; three seconds lets a viewer follow "those nine went there, those sixteen went there". Because the destinations are the pad's actual cell positions and rotations, resolved when the timeline is compiled, the reveal is deterministic and reversible when you scrub, and it re-targets itself if you move the pad. The pad is hidden by starting transparent — a bare fadeOut at 0 s would show it for the first second.
The 3D tumble: spin, arc, stagger. The third argument of moveToEach is optional, and without it the tiles just slide and turn to the cells' orientation. With it they fly. spin: [1, 1, 0] is one whole turn about each of the tile's x and y axes (every tile gets a random sign, so they tumble differently); arc: 3 lifts each tile up to about three tile-widths towards the camera at mid-flight and back down; stagger: 0.4 spreads the start times over 40% of the three seconds and shortens each run to match, so tiles leave in a scatter but all arrive together. Every one of them still ends exactly where the plain move would: whole turns, a lift that is zero at both ends, and a delay paid back by a shorter run. The randomness is a fixed function of each tile's place in the list, so playing, scrubbing and re-rendering give the same tumble. One requirement: the group that holds the tiles must have a uniform scale, because a stretched parent shears a spinning child and multiplies the lift.

8 The sum, read off the screen

Three more labels, copied from eqn so they keep its font, glow and shadow, sit beside the triangle: a on the vertical leg, b on the horizontal one, and c on the hypotenuse, the side opposite the right angle. 9 Two more triples, a quarter turn apart

3-4-5 is not the only right triangle with whole-number sides. Two more, 5-12-13 and 8-15-17, get the same treatment — tiles in a square on each leg that fly onto the square on the hypotenuse — and they are placed around the camera instead of in front of it: the camera starts facing the first, and every quarter turn about Y (90°) brings the next into view. makeTriple builds one from its two legs and hypotenuse, scales it to about the height of the 3-4-5 so it fills the frame the same way, and turns it to face the camera that will be looking at it. The hypotenuse square is made of empty groups, one per cell, because the tiles only need somewhere to land: they are never drawn.

// A Pythagorean triple p-q-c, laid out like the 3-4-5 and built the same way: unit tiles in a square on
// each leg, and an empty landing pad on the hypotenuse for them to fly onto. The figure is scaled to
// about the height of the 3-4-5 and turned to face `yaw` degrees.
function makeTriple(id, p, q, c, target, yaw) {
  const k = 10 / (2 * q + p);
  const outer = new Group();
  outer.name = id;
  outer.position.set(...target);
  outer.rotation.y = THREE.MathUtils.degToRad(yaw);
  outer.scale.setScalar(k);
  const figure = new Group();
  figure.position.set(-q / 2, -p / 2, 0);      // put the figure's bounding box on the target
  outer.add(figure);

  const group = (name, x, y, rotZ) => {
    const g = new Group();
    g.name = `${id}-${name}`;
    g.position.set(x, y, 0);
    g.rotation.z = rotZ;
    figure.add(g);
    return g;
  };

  const triangle = new Mesh(
    new ExtrudeGeometry(new Shape([new Vector2(0, 0), new Vector2(q, 0), new Vector2(0, p)]), { depth: 1 / k, bevelEnabled: false }),
    new MeshStandardMaterial({ color: 0xd99b30, roughness: 0.9, metalness: 1 })
  );
  triangle.geometry.translate(0, 0, -0.5 / k);
  triangle.name = `${id}-tri`;
  figure.add(triangle);

  // n x n tiles; tile (i, j) is centred at place(i, j). One shared geometry, and two shades in a
  // checkerboard, so single tiles stay visible even when they are only a few pixels wide.
  const square = (name, n, color, place) => {
    const g = group(name, 0, 0, 0);
    const geometry = new BoxGeometry(0.9, 0.9, 0.9);   // a cube, with a gap between neighbours
    const shade = [color, new Color(color).offsetHSL(0, 0, 0.09)].map(c => new MeshStandardMaterial({ color: c, roughness: 0.6, metalness: 0.2 }));
    for (let i = 1; i <= n; i++) {
      for (let j = 1; j <= n; j++) {
        const tile = new Mesh(geometry, shade[(i + j) % 2]);
        tile.name = `${id}-${name}.${i}.${j}`;
        tile.position.set(...place(i, j), 0);
        g.add(tile);
      }
    }
  };
  square('p', p, 0xff6b6b, (i, j) => [j - 0.5 - p, i - 0.5]);     // on the vertical leg
  square('q', q, 0x4ecdc4, (i, j) => [j - 0.5, 0.5 - i]);         // under the horizontal leg

  // the hypotenuse square: c x c empty groups, turned onto the slope, no geometry at all
  const pad = group('pad', q, 0, Math.atan2(q, p));
  for (let i = 1; i <= c; i++) {
    for (let j = 1; j <= c; j++) {
      const cell = new Group();
      cell.name = `${id}-cell.${i}.${j}`;
      cell.position.set(j - 0.5, c + 0.5 - i, 0);
      pad.add(cell);
    }
  }

  editor.execute(new AddObjectCommand(editor, outer));
}

makeTriple('t3', 8, 15, 17, [3, 2.88, 40], 180);     // behind the camera's start

Why these tiles have no black borders. The 3-4-5 tiles draw a border by carrying a child line object, and a class on a node also matches everything inside it, so .cube matches both the tiles and their borders. That is harmless when every target is a tile too, but here the targets are empty groups with no borders, so a selector that matched borders would pair the wrong things. These tiles are therefore plain meshes (a little under 1 wide, so a gap shows) in two shades laid out like a checkerboard. They share one geometry and two materials per square; the editor logs a warning that a shared material is animated on several nodes, which is exactly what the fade-in wants.
Why the yaw is the group's own rotation. A camera that has turned yaw° about Y looks along a direction that turns with it, and an object with the same rotation.y has its front toward that camera. So the triple at [-17, 2.88, 20] (20 units to the left of the camera) is turned 90°, the one at [3, 2.88, 40] (20 units behind it) 180°, and the end card on the right 270° (−90°). Because the figure is built inside a scaled, turned group, every position inside it is written in the figure's own flat frame, exactly like the 3-4-5.
Why the targets are at y = 2.88, not 0.68. The camera is at y = 0.68, and makeTriple centres the figure with its hypotenuse square included, but that square stays invisible until the tiles land on it. Before the flight the legs' squares therefore sit low in the frame, and a caption below them falls inside the subtitle band. Raising each figure and its caption by 2.2 units lifts both clear of it; the finished figure, with its hypotenuse square, still fits at the top of the frame.

Each triple gets one caption, copied from the eqn label so it keeps the font, the glow and the size (and gets the shadow flag too), then placed below its figure in the figure's own frame:

// One caption per triple, copied from the first label so it keeps the font, the glow and the size.
const src = $S('#eqn').nodes[0];
function makeCaption(name, target, yaw) {
  const a = THREE.MathUtils.degToRad(yaw);
  const [dx, dy, dz] = [-3.7, -6.5, 1.24];   // below the figure, in the figure's own screen frame
  const label = new Mesh(src.geometry.clone(), src.material.clone());
  label.name = name;
  label.scale.copy(src.scale);
  label.userData.textShadow = true;          // the drop shadow from step 4
  label.rotation.y = a;
  label.position.set(target[0] + dx * Math.cos(a) + dz * Math.sin(a), target[1] + dy, target[2] - dx * Math.sin(a) + dz * Math.cos(a));
  editor.execute(new AddObjectCommand(editor, label));
}
makeCaption('eqn2', [-17, 2.88, 20], 90);
makeCaption('eqn3', [3, 2.88, 40], 180);
$S('#eqn2, #eqn3').addClass('label');

Now the clock. The existing film is untouched up to 56.5 s. After that the beats are spaced for a voice reading the subtitles aloud (see step 11): the theorem stays on screen for nine seconds while its letters are explained, and each triple then gets 22 seconds, and they follow the same beat as the 3-4-5: a 2.5-second quarter turn, the triangle, the two squares of tiles fading in one at a time with their areas as captions, then all the tiles tumbling onto the hypotenuse square (3 seconds, in selector-list order, so the first leg's tiles take the first cells), ending on the sum. 11 Subtitles

Subtitles are cues kept on the scene itself (scene.userData.renderSubtitles), so they are saved, versioned and committed with it. setSubtitles replaces the whole list in one undoable step. Times are output-video seconds, which here equal timeline seconds because the render starts at 0. They show over the viewport while you play or scrub, and the Render tab can burn them into the picture or export an .srt.

Writing cues that fit the picture. Each cue starts with the thing it describes (the leg at 6 and 9 s, the unfolding square at 14 and 24 s) and ends before the next beat; none is longer than two short lines, and none overlaps another. Keep a cue on screen at least about a second for every fifteen characters, and leave room for the voice: a spoken cue needs its text read aloud plus a quarter of a second, so the later cues here are short ("144 tiles.", not a sentence) to finish before the next one starts when dubbed with a text-to-speech tool. exportSrt() returns the same cues as .srt text.

12 Choose the camera and render it

  1. Open the Render tab and click + Add Shot under Camera Sequence. The first shot lands at 0 s on your scene camera, with a cut. Without a shot the render uses the Edit Camera, so none of the quarter turns would be filmed — see Add a static hero camera to a render sequence for what a shot can do.
  2. Pick a resolution and frame rate. The scene camera is authored 16:9 and the card is landscape; a portrait crop is a manual resolution choice.
  3. Optionally set File name. The line under it shows what the download will be called, by default pyth_2m03s_720p_30fps_2026-10-25.mp4: the scene's file, the length of the video (with the two-second hold at the end), the resolution, the frame rate and the date. Type your own template with {project}, {duration}, {res}, {fps}, {date}, {time}, {camera} and {360}, for example Pythagoras {res}.
  4. Click Render & Export and wait — rendering runs in real time, so about a minute and three quarters.
  5. The call card is re-fetched and re-baked fresh at render time at its true aspect — edit /about/callcard later and every future render picks up the change with no edits to this scene.
Everything above is git-versioned. Commit from the Git tab whenever you like — the timeline, the geometry, and the call-card reference (never a copy of its pixels) all round-trip through the same scene JSON. See the animation guide and the call-card guide for the full grammar this tutorial only samples.

13 Open the finished scene

pyth.json in tejaswigowda/test1 is the scene these blocks build: 50 tiles in 12 lines, the triangle, the three labels (and the a, b, c side names), the camera, the background and the call card, plus the two extra triples (458 more tiles, their landing cells and captions), with 25 timeline tracks (the three side names add one each), the same 120.5-second clock and 24 subtitle cues. Open it, then scrub the Animations tab: at 24 s the 3×3 has unfolded, at 43 s all 25 tiles sit on the pad, at 88 s the 5-12-13 sum is on screen, at 112 s the 8-15-17 one, and from 120 s the card fills the frame.

What was checked, and what differs. Every block on this page was pasted, one paste at a time, into an empty scene, with the three Text stencils, the Call card stencil and + Add Shot clicked where the text says so. The result was compared with pyth.json: the same timeline tracks with the same events at the same times (22 of them before the a, b, c side names were added), the same subtitle cues word for word (23 then), and a frame at each of twelve times from 0 to 98 s, chosen away from the flights, that differs from the published one by under 3% of its pixels. The tumbles themselves are not compared pixel for pixel: each tile's flight is a fixed function of its place in the list, and the published file lists its first triple's tiles in a different order, so the same tiles tumble differently there. The final end-card frame (100 s) is the exception: the card is re-baked from the live /about/callcard page every time a scene loads, so it was not compared pixel for pixel. (An older saved copy of this scene stored the card's material as opaque, and at full opacity that drew the QR as a blank white box; the editor now keeps the card blending on every load and render, whatever the saved scene says.) Three small differences are deliberate: the published file keeps its tiles at an offset inside their groups, so two of its positionX/positionY values read 9.4 and 4.4 where yours read 0.4 and −0.6 (the same place in the world); it nests the three labels in a Labels group, which nothing addresses; and its pad cells are numbered in a different order, with the same nine-and-sixteen split. The latest revisions, cube tiles, the label shadow and the a, b, c side names, were checked less thoroughly: the side-name and subtitle blocks were pasted from this page into the published scene, which then matched what was saved (25 tracks, 24 cues); the squares, triangle and triples blocks were pasted into an empty scene and build the same 50 and 458 tiles, now all cubes, and the published scene was played through once on a real GPU, and scrubbed back and forth across every label change, with no rendering errors (the editor used to free a label's old text geometry a frame after swapping it, which made the next draw of that label fail while scrubbing; it now frees it first), but the frame comparison above predates it and the label-shadow lines were not re-pasted from this page. Rendering (step 12) was not re-run for this revision. The film was later stretched from 100.5 to 120.5 seconds so a voice can read every cue without overlap (the beats after 56.5 s moved later, the cues were re-timed to match, and a dub of the .srt reports no overlaps); that revision was loaded and checked for its clock, tracks and cues, but its blocks were not re-pasted and the frames above were not re-compared. The scene file is now about 4.8 MB, nearly all of it baked animation, chiefly the flight paths of the 483 tiles that move; the editor rebuilds them from the timeline on load, so they are a cache, not something to edit.
