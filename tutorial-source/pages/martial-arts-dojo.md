<h1>A martial-arts lesson, then a sparring match, in a bamboo dojo</h1>

<figure>&#10;		<img src="./screenshots/dojo-lesson.png" alt="A student and a bald teacher face each other on a tatami mat inside an open bamboo hut with a calligraphy scroll and paper lanterns">&#10;		<figcaption>The finished scene, seen through the <code>cam-wide</code> camera at 30 s: the teacher demonstrates a kick while the student watches.</figcaption>&#10;	</figure>

<p class="tagline">Two characters, one motion clip. A <strong>teacher</strong> performs a martial-arts routine in short chunks; after each chunk the <strong>student</strong>, who has been standing and watching, repeats it. Around them a bamboo hut with warm lanterns and a low sun, and four cameras that cut between over-the-shoulder, side and wide shots. Everything after the import is the JS Shell and the Render tab, and the finished scene is <a href="../../#repo=tejaswigowda/test1&amp;file=dojo.json&amp;branch=main"><code>dojo.json</code></a> in the <code>tejaswigowda/test1</code> repo.</p>

<figure>&#10;		<img src="./screenshots/dojo-sparring.png" alt="Two fighters sparring on the tatami mat inside the same bamboo hut">&#10;		<figcaption>Part 2 (steps 11–14): the same hut with a second pair of characters, now sparring for 170 s — <a href="../../#repo=tejaswigowda/test1&amp;file=sparring.json&amp;branch=main"><code>sparring.json</code></a>, seen through <code>cam-wide</code> at 12 s.</figcaption>&#10;	</figure>

<div class="note"><strong>Where the pieces come from.</strong> Both characters are VRM models made with <a href="https://tejaswigowda.com/strata-editor/facebind/">facebind</a>. They were rigged and given the animation with <a href="https://tejaswigowda.com/bodyrig-webCLI/">bodyrig-webCLI</a>, which writes one GLB per character with the clip baked in. The motion itself is from <a href="https://arxiv.org/abs/2512.22690">Mesquite MoCap: Democratizing Real-Time Motion Capture with Affordable, Bodyworn IoT Sensors and WebXR SLAM</a> (arXiv:2512.22690). Both characters carry the same clip, named <code>p2</code>, 46.83 s long. Part 2 (step 10 onwards) uses a second pair from the same pipeline whose two clips, <code>st1_1072026Skeleton</code> and <code>st2_1072026Skeleton</code> (170.17 s each), were captured together. That sparring capture was recorded with an OptiTrack system in the course “Martial Arts and Motion Capture” (GAME 294) at Arizona State University, run by <a href="https://search.asu.edu/profile/1795222">Pavan Turaga</a> and recorded by <a href="https://search.asu.edu/profile/215415">Assegid Kidane</a>; see <a href="sparring-from-mocap.html">A sparring match from a two-person motion capture</a> for what to do with it.</div>

<div class="note"><strong>How to follow along.</strong> Open the <a href="../../">editor</a>, import your two GLBs (<strong>Import</strong> in the menu bar), open the <strong>Shell</strong> tab and paste each block in order. Every block goes through an undoable command, so <kbd>Ctrl/Cmd+Z</kbd> backs out a step. The selectors below (<code>.vroidv110malev113bound-15p2glb</code>) are derived from the imported object names; yours will differ, so check with <code>scene.children.map(o =&gt; o.name)</code> and adjust.</div>

<div class="note"><strong>Each Shell command runs in its own scope.</strong> A <code>const</code> or function from one block is not visible in the next, so step 1 stores the shared pieces on <code>window.dojo</code> and every later block starts by pulling out what it needs with <code>const { … } = window.dojo;</code>. Only the bamboo-frame block in step 5 (and, in Part 2, the swap block in step 10 and the shot-list block in step 13) needs <code>await</code>, so only those are wrapped in <code>(async () =&gt; { … })();</code>; the Shell does not print what an async block returns, so they leave their results on <code>window.dojo</code> too. <code>holdTimelineAt(t)</code>, used throughout, is a Shell global that jumps the whole scene to <code>t</code> seconds — exactly what scrubbing the timeline does.</div>

<h2><span class="step">1</span> Import and pick a teacher</h2>

<p class="lede">Import both GLBs. They arrive as two top-level groups, each with its own copy of the clip <code>p2</code>, and the same clip name does not clash because a clip is bound to its own character. Make the bald one the teacher and the other the student; below, the teacher is the group whose name contains <code>(15)</code> and the student the one containing <code>(11)</code>.</p>

<pre><code>const T = scene.children.find(c =&gt; /\(15\)/.test(c.name));   // teacher&#10;const S = scene.children.find(c =&gt; /\(11\)/.test(c.name));   // student&#10;const bone = (root, re) =&gt; { let r = null; root.traverse(o =&gt; { if (!r &amp;&amp; o.isBone &amp;&amp; re.test(o.name)) r = o; }); return r; };&#10;const wp = b =&gt; b.getWorldPosition(new THREE.Vector3());&#10;const hips = ch =&gt; bone(ch, /J_Bip_C_Hips/);&#10;window.dojo = { T, S, bone, wp, hips, plan: [] };</code></pre>

<p>Check it took: <code>window.dojo.T.name</code> and <code>window.dojo.S.name</code> should print the two character names.</p>

<div class="note"><strong>Frame 0 of this clip is a T-pose.</strong> The routine starts from a relaxed stance at about 4.5 s into the clip, so everything below treats <code>4.5</code> as the "rest" time: both characters are held there before and between their turns.</div>

<h2><span class="step">2</span> Put them face to face</h2>

<p class="lede">Imported clips carry <em>root motion</em>: the hips travel through the scene as the clip plays, and the clip's own root node can start well away from the group origin. Placing the groups by their position alone therefore leaves the characters wherever the clip puts them. Instead, measure where the hips are at rest time, then move each group so the hips land on the spots you want.</p>

<pre><code>const { T, S, wp, hips } = window.dojo;&#10;&#10;// Hold the whole scene at the rest stance (this is what scrubbing does), then read where each pair of hips is.&#10;holdTimelineAt(4.5);&#10;scene.updateMatrixWorld(true);&#10;const s0 = wp(hips(S)), t0 = wp(hips(T));&#10;&#10;// Teacher goes to the mirror image of the student across the origin on z.&#10;const target = new THREE.Vector3(s0.x, 0, -s0.z);&#10;const d = target.clone().sub(t0); d.y = 0;&#10;editor.execute(new SetPositionCommand(editor, T, T.position.clone().add(d)));</code></pre>

<p>The pair now stand about 3.4 m apart on the z axis. Next, turn them to face each other. The chest line is the reliable way to measure facing — the angle between the shoulder normal and the direction to the partner — so use it to check, then nudge <code>rotation.y</code> until both read close to 0°:</p>

<pre><code>const { T, S, bone, wp, hips } = window.dojo;&#10;const facingError = (a, b) =&gt; {&#10;  const l = wp(bone(a, /J_Bip_L_UpperArm/)), r = wp(bone(a, /J_Bip_R_UpperArm/));&#10;  const f = l.sub(r).cross(new THREE.Vector3(0, 1, 0)); f.y = 0; f.normalize();&#10;  const to = wp(hips(b)).sub(wp(hips(a))); to.y = 0; to.normalize();&#10;  return +(f.angleTo(to) * 180 / Math.PI).toFixed(1);&#10;};&#10;[facingError(T, S), facingError(S, T)];   // aim for ~0 at the rest stance</code></pre>

<div class="note"><strong>Why measure instead of rotating by 180°.</strong> The clip's root node has its own orientation, so the group's <code>rotation.y</code> that makes a character face its partner is not a round number (the teacher ended up near +92° and the student near +272° here). Measure, then adjust — a few degrees either way is easy to see from above in the viewport.</div>

<p>While the routine plays, the performer turns and kicks, so the facing error grows mid-move. That is the clip, not the placement; at the rest stance both are within a degree or two.</p>

<h2><span class="step">3</span> Teach in chunks: the demo, then the repeat</h2>

<p class="lede">The timeline is a list of directives. <code>$S(selector).at(t).play(clip, { duration })</code> starts a clip, <code>.seek(time)</code> picks where in the clip to start, and <code>.pause()</code> freezes it. Before its first <code>play</code> a clip shows frame 0 (the T-pose), so first park both characters at the rest stance, then play the routine in three chunks:</p>

<ol class="steps">&#10;		<li>The <strong>teacher</strong> demonstrates a chunk of the clip while the student stands at rest.</li>&#10;		<li>One second later, the <strong>student</strong> plays the <em>same</em> chunk while the teacher watches at rest.</li>&#10;		<li>A second after that, the next chunk begins.</li>&#10;	</ol>

<pre><code>const { plan } = window.dojo;                          // [who, start, end] windows on the timeline&#10;const teacher = $S('.vroidv110malev113bound-15p2glb');&#10;const student = $S('.vroidv110malev113bound-11p2glb');&#10;&#10;// Park both on the rest stance: play for 1 s, seek to 4.5 s, pause.&#10;for (const who of [teacher, student]) who.at(0).play('p2', { duration: 1000 }).seek(4.5).pause();&#10;&#10;// Three chunks of the 46.8 s clip, in clip time.&#10;const chunks = [[4.5, 16.4], [16.4, 29.1], [29.1, 46.8]];&#10;let t = 1;&#10;for (const [a, b] of chunks) {&#10;  const len = +(b - a).toFixed(2);&#10;  teacher.at(t).play('p2', { duration: len * 1000 }).seek(a);       // teacher demos&#10;  teacher.at(+(t + len).toFixed(2)).pause();                        // ...and freezes&#10;  student.at(+(t + len + 1).toFixed(2)).play('p2', { duration: len * 1000 }).seek(a);   // student repeats&#10;  student.at(+(t + 2 * len + 1).toFixed(2)).pause();&#10;  plan.push(['teacher', t, +(t + len).toFixed(2)], ['student', +(t + len + 1).toFixed(2), +(t + 2 * len + 1).toFixed(2)]);&#10;  t = +(t + 2 * len + 2).toFixed(2);&#10;}&#10;editor.timeline.toJSON().duration;                    // 90.6</code></pre>

<p>Open the <strong>Animations</strong> tab and scrub. The teacher moves from 1 s to 12.9 s while the student holds still, then the student performs the same moves from 13.9 s to 25.8 s, and so on. Each chunk starts where the last one ended in the clip (<code>4.5 → 16.4 → 29.1 → 46.8</code>), so the lesson walks through the whole routine once, demo then repeat, in 90.6 s.</p>

<div class="note"><strong>Why <code>.seek()</code> after <code>.play()</code>.</strong> A later <code>play</code> restarts the clip's local time at 0, so the chunk's start has to be re-applied each time. <code>duration</code> is in milliseconds and sets how long the clip runs before the next directive can take over.</div>

<h2><span class="step">4</span> A floor with no grid</h2>

<p class="lede">A wood base, a tatami mat on top and a boundary tape make the floor. The important detail is the mat's texture: tatami is usually drawn with dark seams, but those read as a grid under the characters, so paint plain straw with random fibres instead — and the texture still tiles.</p>

<p>Check the characters' feet against the mat: both should be within a centimetre of <code>y = 0</code>. If one floats or sinks, nudge that group's <code>position.y</code> with <code>SetPositionCommand</code>.</p>

<h2><span class="step">5</span> A bamboo hut</h2>

<p class="lede">The hut is built from the same trick everywhere: a <em>pole</em> is a thin cylinder stretched between two points, with a few short rings along it for the bamboo nodes. Collect all the poles into arrays, merge each array into <strong>one mesh</strong>, and the whole frame is a handful of draw calls instead of a thousand. The hut is 20 m long and 15 m wide with an open front, so the cameras fly through it freely, and the sun comes in through the open end.</p>

<pre><code>(async () =&gt; {&#10;const { mergeGeometries } = await import('three/addons/utils/BufferGeometryUtils.js');&#10;const V3 = THREE.Vector3, UP = new V3(0, 1, 0);&#10;let seed = 11; const rnd = () =&gt; <p>Nothing is in the scene yet: the hut group is held on <code>window.dojo.hut</code> until the next block adds the roof and the scroll and puts the whole thing in.</p>

<p>Now the thatch roof: two tilted boxes with a straw texture drawn on a canvas, and a rolled ridge cap. Then a calligraphy scroll on the back wall — drawn on a canvas too, with the characters 武道 ("martial way").</p>

<div class="note"><strong>Keep the cameras inside.</strong> The hut is sized around the camera paths from step 7 — 20 × 15 m, rafters starting 3.5 m up. If you resize it, re-run the check at the end of that step: with the posts, rails and scroll in the way, a camera that moves through one at the wrong moment shows a bamboo trunk filling the frame.</div>

<h2><span class="step">6</span> A grove outside, and the lighting</h2>

<p class="lede">The grove is the same pole helper again: 64 tall stalks scattered outside the hut footprint, leaning a little, with a leaf canopy on half of them, over a green ground plane. It shows through the slats and over the rails and gives the scene a surrounding. The floor from step 4 shrinks to the hut's footprint so the grove ground can take over outside it.</p>

<pre><code>const { mergeGeometries, rnd, std, mesh, addPole } = window.dojo;&#10;const grove = { p: [], n: [] }, leaves = [];&#10;for (let placed = 0; placed &lt; 64;) {&#10;  const x = (rnd() * 2 - 1) * 20, z = (rnd() * 2 - 1) * 20;&#10;  if (Math.abs(x) &lt; 12 &amp;&amp; Math.abs(z) &lt; 10.8) continue;            // keep the hut itself clear&#10;  const h = 8 + rnd() * 5, lx = (rnd() - 0.5) * 0.9, lz = (rnd() - 0.5) * 0.9;&#10;  addPole(grove, [x, 0, z], [x + lx, h, z + lz], 0.07 + rnd() * 0.05, 0.6);&#10;  if (placed % 2 === 0) { const l = new THREE.IcosahedronGeometry(1.5, 1); l.scale(1.7, 0.8, 1.7); l.translate(x + lx, h - 0.4, z + lz); leaves.push(l); }&#10;  placed++;&#10;}&#10;const groveGroup = new THREE.Group(); groveGroup.name = 'Bamboo Grove';&#10;groveGroup.add(mesh('Grove Stalks', mergeGeometries(grove.p), std({ color: 0x8aa23f, roughness: 0.6 })));&#10;groveGroup.add(mesh('Grove Nodes',  mergeGeometries(grove.n), std({ color: 0x4d5a22 })));&#10;groveGroup.add(mesh('Grove Leaves', mergeGeometries(leaves),  std({ color: 0x5c8a33, roughness: 0.95 })));&#10;const ground = mesh('Grove Ground', new THREE.PlaneGeometry(140, 140), std({ color: 0x7b8a47, roughness: 1 }));&#10;ground.rotation.x = -Math.PI / 2; ground.position.y = -0.075; groveGroup.add(ground);&#10;editor.execute(new AddObjectCommand(editor, groveGroup));&#10;&#10;// Shrink the wood floor to the hut footprint (scale on the plane's own x/y axes).&#10;editor.execute(new SetScaleCommand(editor, scene.getObjectByName('Wood Floor'), new THREE.Vector3(21.4 / 60, 16.6 / 60, 1)));</code></pre>

<p>Lighting is five different jobs. A <strong>hemisphere light</strong> fills shadows with warm sky and brown ground bounce; a <strong>low warm sun</strong> through the open end casts the long soft shadows that make the floor read as a floor; a <strong>cool rim</strong> from behind separates the characters from the back wall; and <strong>four paper lanterns</strong> are both a visible mesh and a point light that pools orange on the mat.</p>

<h2><span class="step">9</span> Two things that bite: vanishing parts and slow playback</h2>

<p class="lede">With two VRoid characters the scene holds <strong>83 skinned meshes</strong> — each character is split into dozens (hair strands, face parts, jacket, trousers...) — and that exposes two problems that a single simple character never shows.</p>

<ul>&#10;		<li><strong>Heads and parts disappear while playing.</strong> three.js decides whether to draw a mesh from its bounding sphere, and a skinned mesh's sphere is computed from the <em>bind pose</em>, not the animated pose. A root-motion clip carries a character far from that pose, so the engine culls pieces that are still on screen. The fix is <code>mesh.frustumCulled = false</code> on every skinned mesh.</li>&#10;		<li><strong>Playback is slow.</strong> Each skinned mesh had its own skeleton of 109 bones, so every frame did the 109 bone-matrix updates 83 times. In a CPU profile that one function took about 45% of the time. The meshes of one character already share the same bones, and their inverse-bind matrices differ only by one constant matrix per mesh, so a single skeleton can serve them all if that constant is folded into each mesh's <code>bindMatrix</code>. The skinned vertices came out identical (to about 6e-8) and the 83 skeletons became 2.</li>&#10;	</ul>

<p>You don't have to do anything: both fixes run automatically every time an object is added to the scene (<code>optimizeSkinnedMeshes</code> in <code>editor/js/mesh/skinnedPerf.js</code>), including when a saved scene loads. If a mesh's inverse-bind matrices are not related by a constant, it keeps its own skeleton and is left alone. To see what you have:</p>

<pre><code>const skinned = []; scene.traverse(o =&gt; { if (o.isSkinnedMesh) skinned.push(o); });&#10;({ meshes: skinned.length,&#10;   skeletons: new Set(skinned.map(m =&gt; m.skeleton)).size,&#10;   culled: skinned.filter(m =&gt; m.frustumCulled).length });   // { meshes: 83, skeletons: 2, culled: 0 }</code></pre>

<h2><span class="step">12</span> Play both clips from zero, and do not move them</h2>

<p class="lede">One directive each. Both clips are the same length, so both start at 0 and run to the end together; <code>duration</code> is in milliseconds and is what makes the timeline 170.17 s long.</p>

<pre><code>$S('#f1').at(0).play('st1_1072026Skeleton', { duration: 170170 });&#10;$S('#f2').at(0).play('st2_1072026Skeleton', { duration: 170170 });&#10;editor.timeline.toJSON().duration;       // 170.17</code></pre>

<p>The placement is the part to get right. The two clips share <em>one world frame</em>: their root motion already says where each fighter stands relative to the other at every moment. Drag one fighter by hand and you change that relationship, and the bodies start to overlap. To measure it, sample both skeletons every half second and count the moments when any pair of body points, one from each fighter, comes within 12 cm:</p>

<pre><code>const { f1, f2, bone } = window.dojo;&#10;const re = ['C_Head$', 'C_Chest$', 'C_Hips', 'L_Hand$', 'R_Hand$', 'L_Foot$', 'R_Foot$',&#10;            'L_LowerLeg$', 'R_LowerLeg$', 'L_LowerArm$', 'R_LowerArm$'].map(n =&gt; new RegExp('J_Bip_' + n));&#10;const pts = ch =&gt; re.map(r =&gt; bone(ch, r).getWorldPosition(new THREE.Vector3()));&#10;let overlaps = 0;&#10;for (let t = 0.5; t &lt; 170; t += 0.5) {&#10;  holdTimelineAt(t); scene.updateMatrixWorld(true);&#10;  const A = pts(f1), B = pts(f2);&#10;  if (Math.min(...A.flatMap(a =&gt; B.map(b =&gt; a.distanceTo(b)))) &lt; 0.12) overlaps++;&#10;}&#10;holdTimelineAt(0);&#10;overlaps;      // 1 at the import position; 15 with the bald fighter dragged 1 m along z</code></pre>

<p>Each fighter sits at the position the importer gave it (<code>userData.importNormalize.applied.position</code>), and that is where they should stay. What you <em>can</em> change is where the whole pair stands on the mat, because moving both by the same amount keeps their relationship intact. Sample the hips across the whole clip, take the centre of the box they cover, and shift both groups so that centre lands on the middle of the mat. The same block puts both fighters back at their import position first, so it is safe to re-run, and turns on shadows for the bigger body parts, as in step 6:</p>

<pre><code>const { f1, f2, bone, wp } = window.dojo;&#10;// Start from the importer's positions (this also makes the block safe to re-run).&#10;for (const ch of [f1, f2]) {&#10;  editor.execute(new SetPositionCommand(editor, ch, new THREE.Vector3(...ch.userData.importNormalize.applied.position)));&#10;}&#10;&#10;const hips = ch =&gt; bone(ch, /J_Bip_C_Hips/), box = new THREE.Box3();&#10;for (let t = 0; t &lt;= 170; t += 0.5) {&#10;  holdTimelineAt(t); scene.updateMatrixWorld(true);&#10;  box.expandByPoint(wp(hips(f1))); box.expandByPoint(wp(hips(f2)));&#10;}&#10;const c = box.getCenter(new THREE.Vector3());&#10;for (const ch of [f1, f2]) {&#10;  editor.execute(new SetPositionCommand(editor, ch, new THREE.Vector3(ch.position.x - c.x, ch.position.y, ch.position.z - c.z)));&#10;}&#10;scene.traverse(o =&gt; { if (o.isSkinnedMesh) o.castShadow = o.geometry.attributes.position.count &gt;= 700; });&#10;holdTimelineAt(0);&#10;box.min.toArray().concat(box.max.toArray());   // for these clips: x -1.5..2.0, z -4.3..2.2 before the shift</code></pre>

<div class="note"><strong>Two hips-distance numbers worth knowing.</strong> Across the clip the fighters are between about 1.0 m and 4.2 m apart (hips), so a single fixed camera cannot frame both well the whole way: at 1 m the pair is a tight knot, at 4 m a wide stage. That is what the cameras in the next two steps are built around.</div>

<h2><span class="step">13</span> Cameras that follow the pair</h2>

<p class="lede">Reuse the four cameras from step 7 — they stay in the <code>CAMERAS</code> group — but give them new keys and new jobs. For the lesson the interesting quantity was <em>who is performing</em>. For a spar it is <em>where the pair is and how far apart they are</em>: the midpoint between the hips, and their distance. The two over-the-shoulder cameras are renamed <code>cam-f1-pov</code> and <code>cam-f2-pov</code> (each sits behind its own fighter and looks at the other), and everything is keyed every half second across all 170 s:</p>

<ul>&#10;		<li><code>cam-wide</code> — from the open front of the hut, pulling back as the pair separates: the distance is <code>5.2 + 1.2 × gap</code>, clamped to 6.5–8.2 m, and never past x = 9, because the hut's front ridge pole stands at x = 10.</li>&#10;		<li><code>cam-side</code> — an orbit of ±0.45 rad around the pair's midpoint, with a radius of <code>3.4 + 1.15 × gap</code> (4.4–7.2 m) and a 44° field of view. The small angle and the radius cap keep it inside the rails at z = ±7.5.</li>&#10;		<li><code>cam-f1-pov</code> / <code>cam-f2-pov</code> — 0.8 m behind the watcher's head and 0.5 m to the side, at 1.7 m high, looking at the other fighter's chest.</li>&#10;	</ul>

<h2><span class="step">14</span> Cut by distance, and check every frame</h2>

<p class="lede">With 170 s of continuous action there is no "demo" and "repeat" to cut on, so cut on <em>distance</em>. Every 4.5–5 s, look at the average gap over the next four seconds: if the fighters are nearly touching (&lt; 1.6 m) use the side camera, which keeps both in frame; at mid range (1.6–2.6 m) alternate the two over-the-shoulder shots; when they are far apart (&ge; 2.6 m) alternate wide and side. Never repeat the camera just used, open on the wide, and finish on it. For this pair that is 37 shots.</p>

<p>An over-the-shoulder shot only works if the other fighter really fits in the frame, and it cannot be judged by eye on 170 s of footage. So the block that builds the shot list also tests it: it projects the head, chest, hips and both hands of the fighter being looked at (head, chest, hips, hands and feet of <em>both</em> for the wide and side cameras) through the real, compiled camera at every half-second of every shot, and turns any over-the-shoulder shot that ever misses into a side shot. It writes the list through a small undoable command, so <kbd>Ctrl/Cmd+Z</kbd> brings the previous sequence back.</p>

<pre><code>(async () =&gt; {&#10;  const { Command } = await import('./Command.js');&#10;  const { f1, f2, bone, wp, gap } = window.dojo, END = 170;&#10;  const NAMES = ['C_Head$', 'C_Chest$', 'C_Hips', 'L_Hand$', 'R_Hand$', 'L_Foot$', 'R_Foot$'];&#10;  const B = { f1: NAMES.map(n =&gt; bone(f1, new RegExp('J_Bip_' + n))), f2: NAMES.map(n =&gt; bone(f2, new RegExp('J_Bip_' + n))) };&#10;  const cam = n =&gt; scene.getObjectByName(n);&#10;  const avgGap = t =&gt; { const i0 = Math.round(t / 0.5) - 1, a = gap.slice(Math.max(0, i0), i0 + 8); return a.reduce((s, v) =&gt; s + v, 0) / a.length; };&#10;&#10;  // Shot plan by distance.&#10;  const plan = [{ at: 0, cam: 'cam-wide' }];&#10;  let t = 5, last = 'cam-wide', ots = 0, far = 0;&#10;  while (t &lt; END - 5) {&#10;    const d = avgGap(t); let pick;&#10;    if (d &lt; 1.6) pick = 'cam-side';&#10;    else if (d &lt; 2.6) pick = (ots++ % 2) ? <p>Read <code>window.dojo.shotMisses</code> afterwards: <code>0</code> means every sample of every shot had its subject fully in frame. Then check the other direction — that no camera is ever inside a character or outside the hut.
